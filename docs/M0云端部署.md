# M0：Qoder 公网工程骨架

本阶段对应《MVP方案.md》的 M0：邮箱登录、鉴权任务、持久化状态和事件、刷新恢复，模拟任务明确标识。2026-11-09 Qoder 服务恢复后，已创建 MYolGame 公网站点，开通 Function backend 并应用 12 张表和 2 个索引。正式地址为 https://myol-game-bq5p9vqwgrc.qoder.zone 。后台调度部署位置仍按用户选择待定，因此尚不能标记完整 M0 验收完成。早先 `sites_unavailable` 的记录保留在实施日志中。

## 已实现的运行路径

浏览器 → 同源 Qoder Function → 应用邮箱会话 → 数据库任务队列。
独立云端调度 → 认证的 Function 消费接口 → 原子推进任务行与事件。
浏览器通过有限 SSE 快照流接收事件；流关闭后自动按 Last-Event-ID 重连，只读状态，不重发任务。

- 邮箱＋密码注册／登录、查询会话、退出、修改密码并使所有旧密码版本会话失效。
- WebCrypto PBKDF2-HMAC-SHA256，600000 次迭代及随机盐；数据库只保存密码哈希和随机会话的 SHA-256 摘要。
- `__Host-myol_session` Cookie：Secure、HttpOnly、SameSite=Strict、Path=/，有效期 7 天。写请求必须携带匹配固定 `APP_ORIGIN` 的 Origin，不从请求 Host 推导可信来源。
- 数据库持久化限流，条件写入防止跨实例计数丢失；每邮箱 15 分钟 10 次认证，每账号每小时 20 个新模拟任务，另有固定全站认证保护阈值。此基础限流不能替代平台防滥用与 DDoS 防护。
- `myol_m0_tasks` 同一行包含状态、版本和事件；Worker 条件写入同时核对版本和状态，不存在先更新状态后丢失事件的问题。M0 不执行外部副作用，因此此单行 CAS 足够；不能据此宣称 M1 外部 Agent 的执行恰好一次。
- 创建任务需要 UUID Idempotency-Key；相同账号、同键、同需求恢复原任务，不同需求返回冲突。网络错误不自动重放写请求；页面保留待确认标识供用户显式恢复。
- 任务详情、列表、SSE 和取消均从已验证 Cookie 得到用户 ID，并在数据库查询／更新中限制 owner_id；不接受浏览器指定用户身份。
- `/m0` 显示排队、模拟执行、模拟检查、完成或取消；无游戏产物，不调用模型。云端 `/create` 引导到此页，游戏开发写入暂不开放。
- 本地 `npm run dev` 仍使用本地账号和本地 Agent 路径；与云端邮箱账号不自动迁移。

邮箱目前仅为登录标识，**没有发验证邮件，不声称验证邮箱所有权**；邮件找回、管理员账号面板和真实 AI 均不在这轮代码范围内。

## Qoder 依赖与打包

需要使用当前 Qoder `function_backend`，以 Function 内的业务认证管理用户，数据库不向浏览器授予公共读写。不能将旧 `legacy` 分配直接当作已完成私有数据隔离。

平台 SDK 必须支持 `createSiteContext(request, { forwardApplicationCredentials: true })`；否则默认移除 Cookie／Authorization，应用登录和后台消费无法工作。入口只使用该上下文提供的 request。平台在发布时注入 `_qoder/backend.mjs`，不要创建、复制或上传 `_qoder/`。

```bash
npm run check:cloud
npm test
npm run package:cloud
```

`package:cloud` 在 `.runtime/m0-release/` 生成按白名单选择的部署输入，另生成 `.runtime/myolgame-m0-qoder-inputs.zip` 和逐文件 SHA-256 校验清单。归档只包含静态产物、函数源码、迁移、调度脚本和部署说明，不含账号、会话、密钥或本地运行数据；构建产物与归档不提交 Git。它不是 Qoder 正式草稿，正式平台 ZIP 和 `.qoder.site` 描述文件仍由 `prepare_site` 生成。

准备部署时使用现有工程根目录，`webDirectory` 为 `web/dist`，`functionDirectory` 为 `functions`，`spa` 为 false（云端构建使用哈希路由），`databaseAccess` 为 `read_write`。schemaRef 必须来自目标项目实际迁移后的查询；不伪造站点描述文件、schemaRef、Project/Site ID 或发布成功状态。

站点固定正式 HTTPS origin 已写入非密钥服务端文件 `functions/site-config.ts`；可选 `APP_ORIGIN` 可覆盖它。后台调度启用时才配置 `APP_M0_WORKER_KEY`，其值为至少 32 位高熵随机值，仅在支持的安全设置和独立调度服务的安全环境中保存。当前用户选择暂不部署调度，本次草稿不声明必需的应用 Secret，消费接口按未配置关闭；以后启用需准备声明该依赖的新草稿。不得放入网页、构建变量、命令参数、Git、日志或聊天。平台数据库凭据完全由注入 SDK 管理，不添加应用数据库密钥。

## 数据库迁移

- 新项目：申请 database/functions 能力，选择 `databaseAccessModel: function_backend`。使用最新 [infra/schema.sql](../infra/schema.sql)，其中已包含 M0 表。
- 已有项目：先读取真实 schema 和 access model，再仅补齐缺失结构。M0 增量草案为 [20261109_m0_cloud.sql](../infra/migrations/20261109_m0_cloud.sql)；不要在已建表上重复执行 CREATE TABLE。旧社区模板迁移是否需要执行，以目标结构为准。
- Function backend 使用平台生成的私有策略，迁移 `accessPolicies` 为空；不为密码、会话、私有任务增加 anonymous/public 授权。
- 用 Qoder 会话中的正式迁移工具创建计划、检查实际 SQL 和策略、应用其 planRef，等待完成，再读取并保存新的 schemaRef。同一迁移不能因超时而换 ID 重复执行。

## 独立云端调度

当前已核实的 Qoder 文档只保证 HTTP Function，未核实常驻 Node Worker 或定时触发能力。因此不把 `setTimeout` 或进程内队列当作可靠云端执行。

后台接口：`POST /functions/v1/app/api/m0/worker`，要求独立服务凭据。每次有界读取活动任务，以 CAS 推进一个阶段；中断后数据库保留队列，后续调度继续。不需要模型、Qoder PAT 或浏览器 Cookie。

在选定的**云端** Node 服务中通过安全环境注入两个 APP 配置后运行：

```bash
npm run worker:m0
```

调度脚本每两秒请求一次，使用固定 HTTPS origin，不跟随重定向，请求 15 秒超时，错误只输出固定分类／HTTP 状态，不输出凭据。可由云服务进程管理器负责重启；也可使用已核实的托管定时触发直接调用同一接口。禁止把部署人员本机在线当作公网验收条件。

没有运行调度时任务会保持排队，页面明确提示检查后台；这不能标为 M0 完成。用户已选择本轮先完成 Qoder 部署输入包，调度部署位置待定。具体云主机／托管调度资源尚未选择或部署，不能把一个消费接口等同于已经运行的云端 Worker。

## 发布顺序

1. 在 Qoder 的站点会话恢复正常后，用只读操作识别目标站点，保留现有 Project/Site 绑定和访问范围。本次经用户明确允许，将无效旧描述文件原样备份至 `.runtime/backups/.MYolGame.qoder.site.bak`，平台生成新描述文件；不得手写其字段。
2. 新站点用真实已构建静态文件准备**未发布**的初始化草稿以获得站点身份；配置 database/functions 后端和迁移。不要把初始化草稿当成成品交付。
3. 固定公开来源使用服务端常量或安全配置；后台暂缓时页面必须明确提示任务将保持排队。启用后台时通过支持的安全设置配置后台密钥并确认同步，再启动选定云端调度。当前 CLI 的 secretValueInput=false，不向用户索要聊天中的密钥，也不虚构此宿主的配置编辑器。
4. 以迁移后的 schemaRef 准备完整前端和 Function 草稿，检查 readiness，正式 publish，轮询同一 action，直到验证 `published: true`。
5. 确认正式站点的访问范围符合用户要求。Qoder 站点访问权限和本应用邮箱身份是两层；测试邮箱登录不能替代将站点设为公众可访问。
6. 对正式公网 URL 执行下面的验收。不把静态预览、构建成功或 backend ready 当作运行成功。

## 公网验收清单

- `/api/health` 返回 `milestone: M0`、`simulated: true` 和目标版本，深层页面可直接刷新。
- 两套隔离浏览器注册不同邮箱，验证 Secure/HttpOnly Cookie、登录、退出、改密撤销旧会话；改密后旧口令不能登录。
- A 创建模拟任务，B 不能读、订阅或取消 A 的任务，伪造 Authorization／用户 ID 不能越权。数据库 SDK 在 Function 中使用平台私有凭据，浏览器不直接访问表。
- 创建请求接受后关闭浏览器，独立云端后台继续推进；重新打开或另一浏览器登录后恢复原任务和全部阶段，不产生重复任务。
- SSE 重连从既有序号恢复；重复相同提交键不会产生新任务，取消与 Worker 并发时保持一个确定终态。
- 重启调度进程后继续消费数据库队列；应用重发／网络错误不覆盖已有结果。
- 在目标平台验证应用凭据透传、原子条件写入的受影响行语义、Tenant RLS，以及 Provider 直连／备用入口不能绕过站点与应用限制。

本机测试使用 SDK 契约替身和真实 HTTPS Chrome。远端迁移和正式发布已执行，健康接口返回 M0；用户截图确认普通浏览器能显示邮箱登录页；注册登录、双账号业务流程仍待确认。自动化 Chrome 被平台以 BOT_DETECTED 拒绝，因此未绕过反自动化策略继续业务验收。跨实例高争用、Tenant RLS 和 Provider 直连／备用入口隔离仍需专项验收，后台推进和进程重启验收待调度部署后完成。

## 持续运行前的后续工作

M0 的数据库队列可跨实例和重启保留，但过期会话、限流桶和历史任务当前不会自动清理。正式持续试用前需制定并执行保留与清理策略、备份恢复演练；删除／清理不得自动删除仍需保留的任务或用户数据。M1 再引入真实云端 Agent、构建和浏览器隔离执行，不沿用模拟任务结果冒充真实开发成功。

## 当前云端路由

实测站点首页和 Function 可访问，但 `/account`、`/m0` 在 `spa: true` 草稿中仍返回 404。因此云端构建命令 `npm run build:cloud` 启用哈希路由，正式页面使用 `/#/account`、`/#/m0`；API 仍为 `/functions/v1/app/api/...`。普通本地构建保持 BrowserRouter 路径。云端登录、退出、改密和删除项目后的整页跳转通过统一路由帮助函数生成地址。不要把平台 SPA 配置存在等同于已验证深层路由可用。
